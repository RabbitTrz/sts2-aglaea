## M1 — 万帷网 / 政务处理：异地写入的同步方式

**现象**：这两张牌的效果目的地都在**别的玩家**身上
（`TailorCmd.Summon` → `PlayerCmd.AddPet`；`TailorCmd.AddChrysalisToDrawPile` → `CardPileCmd.AddToCombatAndPreview`），
但我们只传了当前的 `choiceContext`。

**为什么可疑**：
- 我们是**第 9、10 张**（末位）出牌，出牌者的 `choiceContext` 归属出牌者。
- 效果却要落到队友身上。如果引擎的 action queue 不自动把这个 context 的归属转发到对方，
  客户端打出时主机就不会执行对应的远程动作。
- 我一度想加 `choiceContext.ToHostContext()` 强制房主执行 —— **这个 API 是我编的，根本不存在**（编译报错 CS1061）。

**已查证**：原版**没有**任何 context 转换。原版同类牌 `Rally.cs`
（同为 `MultiplayerOnly` + `TargetType.AllAllies`）就是直接：

```csharp
foreach (Creature item in enumerable)
    await CreatureCmd.GainBlock(item, base.DynamicVars.Block, cardPlay);
```

**但**：原版所有 `AllAllies` 牌都是「给队友加 buff」（`Rally` 加格挡），
**没有一张会改写队友的卡组/宠物**。所以 `Rally` 不足以证明我们的用法安全。

**可用的正确构造方式**（若需显式转发）：
```csharp
new HookPlayerChoiceContext(source, ownerPlayer, LocalContext.NetId.Value, GameActionType.Combat)
```
（见 `HookPlayerChoiceContext.cs`；`LocalContext.NetId`、`LocalContext.IsMe(Player)` 都存在）

**待验证**：两人联机，分别由**主机**和**客户端**打出万帷网 / 政务处理，观察队友侧是否真的收到衣匠 / 若虫。

**当前处置**：保持与 `Rally.cs` 一致的写法，未做任何未经证实的转发。**不要**自行发明转换 API。

## M2 — 万帷网：`PlayerCmd.AddPet` 对非本地玩家

**现象**：`TailorCmd.Summon` 内部调用 `PlayerCmd.AddPet<AglaeaTailorMonster>(player)`，
`player` 可能是**队友**。

**为什么可疑**：`AddPet` 是"创建生物"操作，很可能带有本地/权威端假设。
若它只在本地玩家身上生效，队友的召唤会静默失败（不报错，但没衣匠）。

**待验证**：主机打出万帷网后，检查**队友**屏幕上有无衣匠血条与攻击表现。

**备注**：`TailorCmd.Summon` 里还有一段依赖渲染节点的代码
（`NCombatRoom.Instance?.SetCreatureIsInteractable(pet, true)`），
在非本地玩家上下文中行为未经验证。

## M3 — 政务处理：`ChrysalisSwarmPower` 挂在队友身上

**现象**：`TailorCmd.AddChrysalisToDrawPile` 会确保 `player` 身上有 `ChrysalisSwarmPower`，
再往其抽牌堆放若虫。若虫的自动打出逻辑由该 power 驱动。

**为什么可疑**：若该 power 的 hook（`AfterCardDrawn` 或类似）在多端都触发，
则队友抽到若虫时可能**所有端都尝试自动打出一次** → 若虫被打出多次。

**待验证**：队友抽到（主机制造的）若虫时，观察是否只自动打出一次、伤害是否只结算一次。

## M4 — 领袖魅力：`AfterCardPlayed` 的触发端

**现象**：`LeadershipCharmPower.AfterCardPlayed` 现在对**任意玩家**打出的攻击牌计数
（不判断 `cardPlay.Player`，刻意如此，以符合「所有玩家」）。

**为什么可疑**：
- 若 `AfterCardPlayed` 在**所有客户端**都触发一次 → 每张攻击牌被计数 N 次（N=玩家数），门槛形同虚设。
- 若只在**出牌者端**触发 → 你身上的 power 在队友出牌时**根本不会被调用**，
  计数完全不涨，这张牌彻底失效。
- 这两种失效方向相反，但**都致命**，且我无法从静态代码判断属于哪种。

**待验证**（两人联机，A 持领袖魅力）：
1. A 自己打 10 张攻击牌 → 是否获得 1 层至高之姿？（验证本地路径）
2. B 打 10 张攻击牌 → A 是否获得 1 层？（验证远程路径，这是本牌核心）
3. 数一下实际需要多少张才 +1 层：10？20？还是永远不涨？

**注意**：这条若坏，卡牌是"完全无效"而非"数值偏差"，优先级高。

## M5 — 领袖魅力：threshold 的远程一致性

**现象**：`AglaeaLeadershipCharm.OnPlay` 把 `threshold`（10 或 7）当 `Amount` 传给 `Apply`，
`AfterApplied` 里再搬进 `Data.Threshold` 并把 `Amount` 清零。

**为什么可疑**：`Apply` 的 amount 是否在所有端保持一致地传递，未经确认。
若主机算出 10、客户端算出 7（或某人拿到 0），两端门槛不同 → 计数与显示都会错乱。

**相关**：升级状态 `IsUpgraded` 在远程端的同步也依赖引擎。牌本身是升级过的，
两端的 `threshold` 应当一致，但未验证。

**另注**：`LeadershipCharmPower` **没有 `CanonicalVars`**，`Amount` 完全靠 `Apply` 硬塞再搬走。
原版能力牌（如 `Accuracy.cs`、`Afterimage.cs`）走的是 `DynamicVars["XxxPower"].BaseValue`。
当前写法能跑，但偏离原版惯例 —— 若排查 M4/M5 无果，可考虑改回原版惯例再试。

## M6 — 逮捕：触发者必须**排除自己** ✅已定，待改代码

**现象**：`ArrestPower` 只挂在**出牌者**身上（`AglaeaArrest.OnPlay` → 出牌者）。
但 `WeaveLinePower.AfterDamageReceived` 里的判定是：

```csharp
bool arrested = Owner.CombatState?.Players.Any(
    p => p.Creature.GetPower<ArrestPower>() != null) ?? false;
```

**用户裁定（2026-09-20）**：
> 「A 自己的攻击**不能**触发。」

即：逮捕只让**其他玩家**的攻击可触发，**排除逮捕拥有者自己**。

**需要改的代码**：`WeaveLinePower.AfterDamageReceived` 里
`arrested` 成立后还要再排除「dealer 就是逮捕拥有者本人」的情况。
不能简单写成 `dealer.IsPlayer`，而应检查
「dealer 所属玩家 ≠ 持有 ArrestPower 的玩家」。

**待验证**：A 打出逮捕 → **A 自己**的攻击**不应**触发力量下降；
B 的攻击**应**触发。

## M7 — 逮捕：多人下「本回合」= 所有玩家共享回合 ✅已定，无需改代码

**用户裁定（2026-09-20）**：
> 「多人游戏**所有玩家共享回合**。」

即不存在"某个玩家的回合"这种概念，整桌玩家在同一个回合里一起行动，
回合在**所有玩家都结束**后才推进。

**结论**：当前实现（`AfterSideTurnEnd` 里 `participants.Contains(Owner)` 就移除）**语义是正确的**，
因为 `CombatSide.Player` 侧一起结束，Owner 必然在其中。
原文档中「A 的回合结束就移除，B 在 B 的回合打攻击时逮捕已消失」的担忧**不成立** ——
不存在"B 自己的回合"，A 和 B 在同一个玩家回合内。

**注意**：这条同时说明我原先对 STS2 多人回合模型的理解是错的
（我按单人 STS 的"每玩家独立回合"来推断了）。多人下玩家侧是**统一一个 Side**。

**待验证**：A 打逮捕 → B 在同一回合内打攻击 → 力量下降**应**触发。

## M8 — 逮捕 / 间隙织线：加成判定改为**"是否存在"** ✅已定，待改代码

**现象**：`WeaveLinePower.AfterDamageReceived` 里：

```csharp
var player = Owner.CombatState?.Players.FirstOrDefault();
...
if (player.Creature.GetPower<GossamerPower>() != null)   // 脆若游丝
int loss = player.Creature.GetPower<TwistTightPower>() != null ? 2 : 1;  // 绞紧
```

**问题**：`FirstOrDefault()` 取的是**玩家列表第一个**，而不是按语义该取的那个人。
单人时恰好等于自己，所以一直没暴露。

**用户裁定（2026-09-20）**：
> 「只检测**是否有玩家身上存在**这两个 power。」

即不追究"谁打出的"，改为**全场存在性判定**：
只要**任意一名玩家**身上有 `TwistTightPower`（绞紧）或 `GossamerPower`（脆若游丝），
就分别启用「力量下降翻倍」/「力量下降改为提升」。

**需要改的代码**：把
```csharp
var player = Owner.CombatState?.Players.FirstOrDefault();
if (player.Creature.GetPower<GossamerPower>() != null) ...
int loss = player.Creature.GetPower<TwistTightPower>() != null ? 2 : 1;
```
改为
```csharp
var players = Owner.CombatState?.Players;
bool gossamer  = players?.Any(p => p.Creature.GetPower<GossamerPower>()  != null) ?? false;
bool twistTight = players?.Any(p => p.Creature.GetPower<TwistTightPower>() != null) ?? false;
```

**待验证**：A 有绞紧、B 无。B 的攻击触发间隙织线 → 力量下降**应为 2**（存在性判定）。

**未决**：全场存在性判定意味着**队友的绞紧也会强化你的间隙织线**，
反之亦然 —— 力量下降效果事实上对全场共享。
若这不是你想要的，需改为「取 dealer 所属玩家」或「取织线施加者」。

## M9 — 浪漫合奏：跨玩家牌堆操作

**现象**：`RomanticEnsemblePower.AfterCardPlayed` 里对

```csharp
Owner.Player.PlayerCombatState.AllCards.Where(c => c is AglaeaRomanticEnsemble && c.Pile.Type != PileType.Hand)
```

执行 `CardPileCmd.Add(ensembles, PileType.Hand)`。

**已查证（手牌归属问题，✅ 无问题）**：
`CardPileCmd.Add(cards, PileType)` 的实现是
`Add(cards, newPileType.GetPile(cards.First().Owner), ...)`
（`CardPileCmd.cs:354-360`）—— **牌堆由卡牌自己的 `Owner` 解析**。
我们的意图就是"把**我的**牌收回**我的**手牌"，而卡牌的 Owner 正是本牌所有者，
所以归属是**对的**。注意这里用的是 `cards.First().Owner`，
若集合里混有不同 owner 的牌会取错（我们这里都是同一人的，无此风险）。

**仍然可疑（同步方向）**：
1. 触发来源是**别的玩家**出牌（`cardPlay.Player != Owner.Player`），
   操作对象却是 `Owner` 自己的牌堆。这是一个**异地触发 → 本地写入**的组合，
   同步方向与 M1 相反，同样需要验证：客户端触发时主机是否执行。
2. 此逻辑在 `RomanticEnsemblePower.AfterCardPlayed` 中，
   与 **M4 有同一个前置疑点**：队友出牌时，我这端的
   `AfterCardPlayed` 到底会不会被调用？若不会，本牌完全失效。

**待验证**：
- 队友 B 打出攻击牌 → A 的浪漫合奏是否回到 **A** 的手牌？
- 该效果在**主机**和**客户端**分别是否生效？
- 特别地：**B 打出攻击牌时，A 这一端是否收到了 `AfterCardPlayed`**？（与 M4 同源，可一并测）

## M10 — 浪漫合奏：power 层数虚高

**现象**：`AglaeaRomanticEnsemble.OnPlay` 每次都 `Apply(..., 1, ...)`，
`StackType => Counter`，所以打第 2 张会变成 2 层。

**问题**：`RomanticEnsemblePower` 的逻辑**完全不读 `Amount`**（只判断 power 是否存在），
所以层数纯属显示噪音，图标上会显示「2」但效果和「1」一样。

**建议**（待你定）：改为 `PowerStackType.Single`，或重复打出时不再 Apply。
**严重度低**（仅显示问题，不影响功能）。

## M11 — 通用：`Random.Shared` 的跨端一致性 ★最高优先级

**现象**：以下 4 处都用了 `System.Random.Shared`（进程级、系统种子的随机数）：

| 位置 | 用途 |
|------|------|
| `TailorCmd.cs:186` (`PickTarget`) | 随机选敌人 |
| `TailorCmd.cs:221` (`AttackOnce`) | 随机选衣匠 |
| `SpreadingThreadPower.cs:51` | 传线连绵：随机选敌人 |
| `AglaeaEmberSeed.cs:109` | 火种：随机抽一个专属遗物 |

**已查证（高置信）**：原版 `Core/` 里 `System.Random.Shared` **只出现 1 次**，
且在 `Debug/SentryService.cs:604` 的**遥测采样**中 —— 无一处用于游戏逻辑。
原版游戏逻辑一律走可序列化的 `Rng`。

**结论**：`Random.Shared` **不**是游戏的可同步 RNG。多人下各端各自抽随机数 →
选中不同的衣匠 / 不同的目标 → **表现不同步**，且当随机结果影响状态时（受影响目标不同）
会真正分叉，甚至可能导致不同端状态不一致。

**正确的替换方式**：
```csharp
// 原版范例：HauntPower.cs:27
var target = Owner.Player.RunState.Rng.CombatTargets.NextItem(hittableEnemies);

// 原版范例：FragrantMushroom.cs
... .StableShuffle(base.Owner.RunState.Rng.Niche)
```
`RunRngSet` 提供：`UpFront`、`Shuffle`、`UnknownMapPoint`、`CombatCardGeneration`、
`CombatPotionGeneration`、`CombatCardSelection`、`CombatEnergyCosts`、**`CombatTargets`**、
`MonsterAi`、`Niche`、`CombatOrbGeneration`、`TreasureRoomRelics`。

**待验证**：联机下同一张牌在两台机器上是否选中同一目标。
**预计会分叉**（基于原版惯例判断，置信度高）。

**备注**：这条**不只影响多人牌** —— 衣匠体系的**所有**攻击都经 `TailorCmd.PickTarget` / `AttackOnce`，
所以这是**最可能在实际游戏里第一个暴露**的问题。虽然严格说它是"多人下的 RNG"问题
而非多人牌的问题，但影响面覆盖全部 5 张多人牌 + 整个衣匠体系，故列在首位。

## M12 — 绞紧不可叠层 ✅已裁定为「符合设计」，**无需改动**

**用户提问（2026-09-20）**：「绞紧叠加的效果是什么？」
**用户裁定（2026-09-20）**：「绞紧**不累层，没有问题**。」

**当前实现（即最终设计）**：
- `TwistTightPower.StackType => PowerStackType.Single`（`Amount` 隐藏、恒为 1，不叠层）
- `WeaveLinePower` 判定 `!= null ? 2 : 1` —— 只看存在性，不读层数
- `AglaeaKnotTight.OnPlay` 每次 `Apply(..., 1, ...)`

**结论**：绞紧**明确设计为不可叠加**，打出第 2 张绞紧与第 1 张效果相同（×2）。
这是**有意的**，不是实现缺口。**无需改代码或文案。**

> 用户确认翻倍效果不随层数增长就是预期行为。

## M13（新）— 移除临时力量下降会触发 `AfterRemoved`，且**原版自带「效果结束」漂浮文字**

```
  → Creature.RemovePowerInternal

  → NPowerRemovedVfx.Create            // 受 power.ShouldPlayVfx 把关
```

`NPowerRemovedVfx` 用的就是 vfx 键 `POWER_WEARS_OFF`，并带上该 power 自己的

## M14（新）— 史诗终结的伤害加成写法会**写坏存档** ✅已修

**用户原话**：「伤害加成只会在这一次攻击生效」。
**核实结果：原写法**不能**保证这一点。** 已改为与「命定共舞」一致的局部变量写法。

**原写法的问题**：

```csharp
DynamicVars.Damage.BaseValue += removed * DynamicVars[_perStackKey].BaseValue;
await CommonActions.CardAttack(this, cardPlay).Execute(choiceContext);
```

`BaseValue` 是**可写**属性（`DynamicVar.BaseValue { get; set; }`，setter 里
`_baseValue = ...; ResetToBase();`），而且改的是**这张卡牌实例自身**的
`DynamicVars`（`CardModel._dynamicVars`）。

游戏内确实"只生效一次"，靠的是**两个隐式前提**：

1. **没有别的钩子读 `BaseValue` 的残留值。** 已逐个核实所有
   `DynamicVar` 子类的 `UpdateCardPreview`：全都读 `BaseValue`/`EnchantedValue`
   然后写 `PreviewValue`，**没有一个回写 `BaseValue`**。
   所以残留值只影响"下一次打出这张牌时的底伤"，不会污染显示。
2. **同一张卡牌实例不会被打出第二次，也不会带着脏值落盘。**
   这是最脆的一环 —— 卡牌实例会进牌堆，而牌堆**会随存档序列化**。
   一旦带着被改过的 `BaseValue` 落盘，**下次读档这张牌的基础伤害就永久偏大**。

**已修**（`AglaeaEpicFinale.OnPlay`）：跟「命定共舞」一样，把加成算进**本次攻击的
局部变量**，不碰 `DynamicVars`：

```csharp
int damage = DynamicVars.Damage.IntValue
    + removed * DynamicVars[_perStackKey].IntValue;

await CreatureCmd.Damage(
    choiceContext, target, damage, ValueProp.Move, cardPlay.Player.Creature);
```

**顺带修的（同一次改动）**：补上 `cardPlay.Target` 的 null 检查（见 M15），
并把 `CommonActions.CardAttack` 换成显式 `CreatureCmd.Damage`，与「命定共舞」统一。

## ✅ (1) 史诗终结：指向目标后不显示最终伤害

**问题**：这类「按层数缩放伤害」的牌，指向目标后卡面应显示**结算后的总伤害**，
但原实现用的是 `DamageVar`，卡面恒显示基础值 1（只有 `{PerStack}` 那个脚注会变）。

**参考原版**：`PerfectedStrike` —— 用
`CalculationBaseVar(6)` + `ExtraDamageVar(2)` +
`CalculatedDamageVar(ValueProp.Move).WithMultiplier(...)` 三件套。

**关键机制**（`CalculatedVar.cs:73-87`）：
```csharp
decimal num = (CombatManager.Instance.IsInProgress && cardModel.CombatState != null)
    ? _multiplierCalc(cardModel, target) : 0m;
return GetBaseVar().BaseValue + GetExtraVar().BaseValue * num;
```
→ **战斗外 `num = 0`，只显示基础值**；战斗中指向目标则显示
`基础 + 每层加成 × 乘数`。这正是用户说的「战斗外也会显示基础值」。

**类型约束**：`DynamicVarSet` 的访问器是**强转**（`DynamicVarSet.cs:28-44`）：
```csharp
public CalculatedDamageVar CalculatedDamage => (CalculatedDamageVar)_vars["CalculatedDamage"];
public CalculationBaseVar CalculationBase   => (CalculationBaseVar)_vars["CalculationBase"];
public ExtraDamageVar ExtraDamage           => (ExtraDamageVar)_vars["ExtraDamage"];
```
所以三个 var **必须用精确类型**，不能拿泛型 `DamageVar` 顶替。

**改动**（`AglaeaEpicFinale.cs`）：
```csharp
protected override IEnumerable<DynamicVar> CanonicalVars => [
    new CalculationBaseVar(1m),
    new ExtraDamageVar(3m),
    new CalculatedDamageVar(ValueProp.Move).WithMultiplier(
        static (card, _) => CountRemovableStacks(card.Owner.Creature))
];
```
```csharp
private static decimal CountRemovableStacks(Creature? creature)
{
    if (creature == null) return 0m;
    int stacks = PositiveAmount<GoldenThreadPower>(creature)
        + PositiveAmount<SupremePosePower>(creature)
        + PositiveAmount<StrengthPower>(creature)
        + PositiveAmount<DexterityPower>(creature);
    return stacks;
}
```
`OnUpgrade` 从 `DynamicVars[_perStackKey].UpgradeValueBy(2m)` 改为
`DynamicVars.ExtraDamage.UpgradeValueBy(2m)`。

**口径必须一致**：`CountRemovableStacks` 与 `RemoveAll<T>` 严格同源
（同类型只算一个实例、只在 `Amount > 0` 时计入，负数力量/敏捷不计），
否则**卡面预览与实战伤害会对不上**。

**文案**：`{Damage:diff()}` → `{CalculatedDamage:diff()}`，
`{PerStack:diff()}` → `{ExtraDamage:diff()}`（与完美打击对齐）。

> ⚠️ 未知：`WithMultiplier` 在 `CountRemovableStacks` 真的返回 0 时
> （比如一张符合条件的效果都没有），预览是否仍能正确算出 1。
> 完美打击几乎不可能为 0，所以原版没暴露这个边界。待测试确认。

## ✅ (3) 致命浪漫的 smartDescription 不随叠层变化

**问题**：硬编码「造成2倍伤害」，叠到 2 层实际是 3 倍，文案不动。

**参考原版**：`TRACKING_POWER.smartDescription = "…额外受到[blue]{Amount}%[/blue]伤害。"`
—— 直接吐 `Amount`，因为追踪的 `GetMultiplier` 是 `1 + Amount/100`，
`Amount` 本身就是「额外百分比」。

**但致命浪漫不能照抄**：其倍率是 `1 + Amount`，图标上的 `Amount`
**不是**玩家想看的数字（1 层显示 1，但效果是 ×2）。

**方案**：不覆写 `DisplayAmount`（会污染所有显示 `{Amount}` 的地方），
改用 **SmartFormat 条件格式化器**把 `Amount` 映射成倍率。

**ZHS 最终文案**：
```
{OnPlayer:你的[gold]衣匠[/gold]攻击|攻击}临时[gold]力量[/gold]下降的敌人时，伤害×[blue]{Amount:cond:>1?{Amount:abs()}|2}[/blue]
```
渲染验证（逐值模拟）：

| Amount | 渲染 |
|---|---|
| 0 / 1 / -1 | `伤害×2` |
| 2 | `伤害×2` |
| 3 | `伤害×3` |
| 4 | `伤害×4` |

**关键坑**：最初写的是 `{Amount:cond:<0?2|+1?2|>1?+1|}`，**不成立** ——
C# 会优先匹配 `+1` 这个**显式精确 case**，再回落到**空默认值**，
于是 `Amount = 1` 时渲染成空字符串而非 `2`。改为「先判 `>1`，否则一律 `2`」后正确。

**格式化器来源**（已核实，非猜测）：`LocManager.cs:234` 注册的是
**SmartFormat 自带**的 `ConditionalFormatter` / `ChooseFormatter` /
`PluralLocalizationFormatter` / `SubStringFormatter` / `IsMatchFormatter`，
外加原版自定义的 `AbsoluteValueFormatter`(`abs()`)、
`HighlightDifferencesFormatter`(`diff()`)、`PercentMoreFormatter`(`%more()`)、
`PercentLessFormatter`、`ShowIfUpgradedFormatter`、`EnergyIconsFormatter`、
`StarIconsFormatter`、`LocaleNumberFormatter`。
**没有通用算术格式化器** —— 所以求幂等运算不能写在文案里，只能另想办法。

## ✅ (4) 逐火之路卡牌文本升级后仍显示 1

**问题**：`OnPlay` 里写 `int layers = IsUpgraded ? 2 : 1;` —— **临时局部变量**，
升级钩子完全碰不到它，卡面 `获得1个` 是**写死的字面量**，永远不会变成 2。

**改动**（`AglaeaEmberPath.cs`）：
```csharp
protected override IEnumerable<DynamicVar> CanonicalVars => [new DynamicVar("Amount", 1m)];

protected override async Task OnPlay(PlayerChoiceContext choiceContext, CardPlay cardPlay)
{
    await PowerCmd.Apply<EmberPathPower>(
        choiceContext, cardPlay.Player.Creature,
        DynamicVars["Amount"].IntValue, cardPlay.Player.Creature, this);
}

protected override void OnUpgrade()
{
    DynamicVars["Amount"].UpgradeValueBy(1m);
}
```
**文案**：`获得1个遗物` → `获得{Amount}个遗物`

> 教训：**凡是卡面要根据升级变化的数值，就必须走 `DynamicVar` + `OnUpgrade`**，
> 不能在 `OnPlay` 里写 `IsUpgraded ? A : B` —— 那个分支只影响战斗结算，
> 卡面渲染读的是 `DynamicVars`，两边会劈叉。

## ✅ (5) 火种战利品：点击后格子不消失、但无法再点击

**用户指示**：「关于战利品：尝试自定义」→ 先用**方案甲**（延迟删除）。

**根因**：`RelicReward` 点击后走 `RelicCmd.Obtain`，对已拥有的遗物它会
**新建一个实例**并加入遗物列表，于是 `AfterObtained` 里要合并两个实例。
原实现删的是 `this`（新实例），结果炸在这里：

```csharp
// NRelicInventory.AnimateRelic
_relicNodes.First(n => n.Relic.Model == relic)   // First，不是 FirstOrDefault
```
`RelicRemoved` 事件会在 `AnimateRelic` **之前**把对应节点移出 `_relicNodes`，
于是 `First` 抛 `InvalidOperationException`，`NRewardButton.GetReward` 的续行
`EmitSignal(RewardClaimed)` **不再执行** →
表现就是「**格子不消失，但已 Disable 无法再点**」。

**改动**（`AglaeaEmberSeed.AfterObtained`）：删**旧实例**，保留 `this`
```csharp
var existing = Owner.Relics.OfType<AglaeaEmberSeed>().FirstOrDefault(r => r != this);
if (existing == null) return;

await GainEmbers(new BlockingPlayerChoiceContext(), existing.Embers);
await RelicCmd.Remove(existing);
```
删旧实例不影响 `ClaimedRelic`（= `this`），动画与信号流程均正常。

**附带确认（此前已查）**：`Reward` 的**自定义子类不可行** ——
`Reward.FromSerializable` 对未知 `RewardType` 直接抛 `NotImplementedException`，
`RewardType` 是内置枚举，扩展不了。所以「自定义战利品」这条路本就堵死，
延迟删除是正解。

## ✅ (5-补) 火种不叠层 —— 上一轮的修法本身是错的

**用户复测**：「其他的都没问题，就只剩一个问题：火种不会叠层了」

### 我上一轮的错误

上一轮我把 `AfterObtained` 写成：
```csharp
await GainEmbers(new BlockingPlayerChoiceContext(), existing.Embers);   // ❌
```
语义是「把旧的 7 层搬过来」，而不是「在旧的 7 层基础上 +1」。
玩家已有 7 层、这次该 +1 → 正确是 **8**，实际算出 **7**。
**这次真正该加的那 1 层从没被加过**，所以表现为完全不叠层。

### 更严重的是：我当时的论证也是错的

我在注释里写「`RelicCmd.Obtain` 已经替我们把『已有遗物』这一半做好了，
它只做 `FindExistingInstanceForStacking` → `ModifyAmount`」——**这是编的**。

实测两个命令完全不同：

```csharp
// PowerCmd.Apply —— 有去重
PowerModel powerModel = FindExistingInstanceForStacking(power, target, applier);
if (powerModel != null) { await ModifyAmount(...); return; }

// RelicCmd.Obtain —— 完全没有去重
player.AddRelicInternal(relic, index);   // 直接 Add
...
await relic.AfterObtained();             // 每次都调
```

`FindExistingInstanceForStacking` **只存在于 `PowerCmd`**（`PowerCmd.cs:169`），
遗物侧没有任何对应物。我误把 Power 的叠加机制套到了 Relic 上。

**旁证**：原版所有「一次战斗可能掉两个遗物」的牌都刻意**只发 `CardReward`、
从不发 `RelicReward`** —— `TheHunt`、`ForbiddenGrimoirePower`、`SwipePower` 全是。
而 `RoyaltiesPower` / `PaelsWing` 这类真发遗物的，走的是 `RelicController.ObtainRelic`
的独立同步路径（非 `RelicReward`），且 `PaelsWing` 只从 grab bag 抽**唯一**遗物
并带 `TestRngInjector` 确定性 RNG。

### 正确的修法（保留「火种自己存层数」的设计）

**「遗物自己存层数」没问题** —— 原版 `PaelsWing` 就是这么干的
（`[SavedProperty] int RewardsSacrificed` + `ShowCounter => true`），
`AglaeaEmberSeed` 与之同构。要修的只有「多实例并存」带来的合并逻辑：

```csharp
public override async Task AfterObtained()
{
    var choiceContext = new BlockingPlayerChoiceContext();
    var existing = Owner.Relics.OfType<AglaeaEmberSeed>().FirstOrDefault(r => r != this);

    if (existing == null)
    {
        // 首次获得。新实例的 Embers 默认是 0（ToMutable() 的 MemberwiseClone
        // 把规范单例的 0 原样带过来），不补这 1 就是 0 层。
        await GainEmbers(choiceContext, 1);
        return;
    }

    // 叠加：旧层数 + 本次 1 层。注意是 existing.Embers + 1，不是 existing.Embers。
    await GainEmbers(choiceContext, existing.Embers + 1);
    await RelicCmd.Remove(existing);
}
```

两个分支是 **if/else 互斥**，不能串联 —— 首次走前者、叠加走后者。

**为什么删旧实例、留 `this`**：`NRelicInventory.AnimateRelic` 跑在 `AfterObtained`
**之后**，内部是 `_relicNodes.First(n => n.Relic.Model == relic)`（**First**，不是
`FirstOrDefault`）。删 `this` 会让 `RelicRemoved` 先移走节点，`First` 抛
`InvalidOperationException`，`GetReward` 的续行 `EmitSignal(RewardClaimed)` 不再执行
→ 表现为「格子不消失，但已 Disable 无法再点」（这正是最初的 (5)）。
删旧实例不影响 `ClaimedRelic`（= this）。

### 已知残留（未修，待用户决定）

`RelicReward.ToSerializable()` 只存 `PredeterminedRelicId`，**不存遗物实例状态**。
而 `CombatRoom.FromSerializable`（`CombatRoom.cs:106`）会用 `Reward.FromSerializable`
把 reward 重建进**同一个 `_extraRewards` 字典**，`RewardsSet.cs:96` 又无条件 concat。

所以流程是「战后 → `AfterCombatEnd` 塞 `RelicReward` → 玩家**离开房间前**退出游戏重进」时：
战后立刻存档（`AfterCombatEnd` 不会跑）→ 读档 → **`AddExtraReward` 再塞一份 +1 的
`RelicReward`** → 恢复的 +1 与原 +1 共存 → 结算 +2 层。

触发窗口很窄（必须卡在战后、领奖励前退出重进），**暂不修**。若要修，
方向是让玩家侧的状态可推导，或在 `AddExtraReward` 里对火种做幂等。
